# Design

## Context

`cargo xtask bench` (`xtask/src/bench.rs`) measures how fast tools build an import graph. It pins public repositories in `bench/bench.toml`, clones them at a commit (`bench/setup.rs`), installs the Node tools with pnpm into `bench/tools/node`, unpacks codebase-memory-mcp into `bench/tools/cbm`, describes the machine (`bench/machine.rs`) and writes a results file through a temporary file that refuses local paths (`bench/results.rs`). The agent benchmark reuses all of it and adds what speed does not need: questions with answers that no tool under test computed, Claude Code runs that see only the tools of their setup, and scores.

## The questions

- Two kinds, both about one exported function: `users`, the other files that refer to it, which an agent needs before it renames or changes a signature; and `tests`, the test files that break when it breaks, which an agent needs to know what to run.
- The answers come from tools that are not under test. `users` uses the TypeScript language service (`findReferences`) of the pinned TypeScript, run by a Node script in `bench/agents/`. `tests` makes the function throw and runs the repository's own tests with the Vitest JSON reporter. Static reachability says which tests could be affected; a failing test is the ground truth that one is. A report that is not Vitest's JSON stops the draw, and so does a run without a throw that reports no test file: neither is a run without failures.
- A test file is in the answer when it fails in both runs with the throw and passes in both runs without it, so a flaky file is in no answer. A file that passes in both runs without the throw and fails in only one of the two runs with it is out of the answer and kept with the question, because the throw or the run may have broken it, and so are the files that fail without the throw: both are scored as neither right nor wrong, since no agent can know them. A file is never in the answer and in the ignored files at once, and the questions file is refused when one is. A run with the throw that outlives its limit, which holds for the build and for the tests each, is passed over as `a run outlived its limit` and not as a run that wrote no report: the draw counts the two apart, since a function that makes a test wait says something different from a run that ended and left none.
- Only TypeScript repositories get questions, because the language server is TypeScript's. Each repository names a scope: `packages/vite` for vite, whose other packages import vite by its package name through `dist`, which the language service cannot follow in a checkout that is not built; the whole checkout for excalidraw, whose tsconfig maps its packages to their sources. Vitest does not start in vite until `packages/vite/dist` exists, because its config imports vite through `dist`, and the tests of the other packages import vite through it too, so vite also pins a `build` command (`build-bundle`, about a second). The draw runs it once after the install, which is the tree the language service reads, and the oracle runs it from the tree as it is right before every run of the test command, the two without a throw and the two with one, so that a test file that reaches the function only through `dist` fails when the function throws, as it would for a developer who builds before testing: a bundle built once before the first throw would never hold one. The oracle builds once more after every restore, so the checkout never ends with a throw in `dist`. The build goes through the same limited, stoppable runner as the tests, with a log of its own beside theirs (`<run>-build.log`). A build that fails with a throw in place passes the function over, and one that fails without a throw stops the draw with an error that names its log. The runs are made in a checkout of their own, cloned again at the same commit, installed and never built: an agent asked for the users of a function would otherwise find build output beside the sources, and two of the tools under test would index it. Only vite gets questions of the kind `tests`: excalidraw installs with yarn, and its lockfile is the only thing that pins what its tests run against.
- The candidates of a kind are the exported functions of the scope, with `export function` and `export const name = (…) =>` or `= function`, declared in a file that is not a test and not a declaration file; `tests` also needs a block body and a function that is not a generator, since calling a generator runs none of its body (an async function stays, because a throw in its body is a rejected promise). The Node script lists them with their referring files and the offset of their body once, and the draw in Rust takes them in the order of the SHA-256 of `seed`, repository, file and name until enough of them qualify. The script refuses to answer when a relative import or a path of the tsconfig inside the scope does not resolve, since a language service that misses a file gives answers that miss its references.
- A question holds its prompt, so the file shows exactly what the agent was asked. The prompt says what counts (by name, in every other TypeScript file, since the language service reads no other: imports, named re-exports, uses; or the unit tests run by the pinned command, when the function fails every time it is called, by throwing an error or, if it is async, by returning a promise that rejects with one), forbids changing files and running the tests, and asks for the last block marked `files`.

## The runs

- Every run is `claude -p` with the pinned model, `--output-format stream-json --verbose`, `--no-session-persistence`, `--permission-mode bypassPermissions`, `--setting-sources project`, `--tools` of its setup, `--max-turns` with the pinned limit, and the prompt on standard input, in the checkout of the runs. `claude --help` of 2.1.312 does not list `--max-turns`, but a run honours it and ends with the result `error_max_turns`.
- The environment of a run is built, not inherited: it holds the variables a program needs to find its home, its login and the network (`HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LC_ALL`, `TERM`, `CLAUDE_CONFIG_DIR`, the proxy variables, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `NODE_EXTRA_CA_CERTS`), the PATH below, `TMPDIR` and `CLAUDE_CODE_TMPDIR` set to the temporary directory of the run, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, `DISABLE_AUTOUPDATER=1`, which keeps Claude Code from replacing itself between two runs of one task, and `ENABLE_CLAUDEAI_MCP_SERVERS=false`. Nothing of the session the task runs inside reaches a run, so a run started from inside Claude Code is not taken for a nested one and no `CLAUDE_CODE_*` or `ANTHROPIC_*` variable changes what it loads.
- `plain`, `lsp` and `cbm` pass `--strict-mcp-config` with a config of their own (empty, empty and codebase-memory-mcp). `gsttt` passes `--plugin-dir` with this repository's `plugin/` and no strict config, because a strict config also drops the servers of plugins. `lsp` passes `--plugin-dir` with a plugin the task writes, whose manifest has only `lspServers`, running the pinned typescript-language-server with the pinned TypeScript.
- The PATH is built from the directories of the programs a run needs, never from the PATH of the machine, because `~/.local/bin` holds both `claude` and an installed gsttt: a directory that holds a link to `node` and nothing else, since the language server is a script of `node` and the directory `node` is installed in holds every program installed beside it (`npm`, `pnpm`, and on some machines a `claude`), and the four system directories. The binary under test is an argument of the task, `--gsttt <binary>`, which `run` requires. It is copied alone into `.bin` of a directory of the task's own, `gsttt-agents-task` under the temporary directory of the system, which also holds `.setups` with the files of the setups: beside the checkouts and not in the directory that holds them, where `ls ..` in a run would list it (the link to `node` is in `gsttt-agents-node` beside it, and what an earlier version of the task left in the directory of the checkouts is removed when the task starts). `.bin` is prepended to the PATH of the `gsttt` setup and of no other, the same copy builds the gsttt index of the checkouts, and its `--version` is recorded among the versions of the tools. A directory of the PATH that holds a program called `claude`, `codebase-memory-mcp`, `typescript-language-server` or `tsc`, or, in a setup but `gsttt`, `gsttt`, stops the task before the first run: the command line of every setup in each of its arms is built once before it for that, and again for every run. The Bash tool of a run builds its shell from a snapshot of `~/.zshrc`, which carries the zsh functions and aliases of the user into every setup alike (232 functions on the machine of the probe, none named after a program of a setup), and whose last line exports the PATH of the `claude` process again: the PATH of the Bash of a run was measured equal to the one the task builds, byte for byte, in all four setups.
- The checkout of the runs lives under the temporary directory of the system: under `~/git` or this repository a CLAUDE.md of a parent directory would reach every run, and so may an AGENTS.md, since Claude Code ships a plugin that reads one (`cc-plugin-agents-md`). The task checks the parents for either before it prepares anything.
- One task at a time. The task keeps its checkouts, the copy of the binary, the files of the setups, the link to `node` and the temporary directories of the runs under fixed names in the temporary directory of the system, empties or replaces them when it starts, and ends every process below the checkouts after a run. Two tasks at once (`questions` and `run`, or two `run`) would empty each other's directories, end each other's runs and each write its own copy of the results over the other's, so that finished runs would be asked, and paid for, again. `questions` and `run` therefore take an exclusive lock on `gsttt-agents.lock` in the temporary directory of the system before they do anything else (`File::try_lock`, which is `flock`) and hold it to their end. The system frees it when the process ends, however it ends, so a task that was killed leaves no lock behind. A second task is refused with a message that names the file. `table` only reads the results and takes none.
- The isolation was measured, not assumed. The probe asked whether the context of the run held the phrase `No sound, ever`, which only the global CLAUDE.md of the machine holds. With the flags above and the environment of a run it answered "No. The phrase `No sound, ever` doesn't appear anywhere in my context." The same command without `--setting-sources project`, without the strict config and with the environment of the session answered "Yes. The line is in the global rules from `~/.claude/CLAUDE.md`: - **No sound, ever.** Never run `say`, `afplay` …", and its init event listed the MCP servers, the plugins and the skills of the machine.
- What a run can reach is set by `--settings`, whose JSON one function builds (`settings` in `xtask/src/agents/setups.rs`): `sandbox` with `enabled`, `failIfUnavailable` and `autoAllowBashIfSandboxed` true and `allowUnsandboxedCommands` false, `filesystem.allowWrite` the checkout of the run and its temporary directory, `filesystem.denyRead` the denied directories, and in `permissions.deny` one rule `Read(//<absolute path>/**)` for each of them, since the sandbox confines the commands of the Bash tool and not the Read tool, and two slashes make the path of a rule absolute (the rule was enforced under `bypassPermissions` and `--setting-sources project`). Every path is given in the name it has and in its canonical one, because the temporary directory of macOS is behind a link and the sandbox matches the path that is opened. Denied are this repository, which holds the sources of the tool under test, the questions and the results; the configuration directory of Claude Code (`CLAUDE_CONFIG_DIR`, else `~/.claude`), which holds the CLAUDE.md, the memory and the transcripts of the user; and the directory of the binary under test and of the files of the setups, which tell a run what the other setups have. The `gsttt` setup is denied `.setups` and not the whole directory, because a denied directory is also one the Bash tool cannot start a program from (measured with the settings of a run: `.bin/gsttt` ran with only `.setups` denied, and failed with `Operation not permitted` when its parent was denied) and that setup has to start `.bin/gsttt`; the other three are denied the whole directory. The sandbox confines the commands of the Bash tool only, not `claude` itself, its MCP servers, its language servers or its hooks.
- A run whose sandbox is unavailable does not go on without it. `failIfUnavailable` makes Claude Code exit at start-up (as its documentation says; this path was not exercised, since the sandbox is available on the machine of the probe), which the harness meets as a process that exited without an init event, `the stream in <transcript> holds no init event after <the time the run took>: <the tail of its standard error>`: the task stops with that error and records nothing for the run, as for any run that ends without a result.
- Neither `TMPDIR`, `CLAUDE_CODE_TMPDIR` nor `CLAUDE_TMPDIR` moves the temporary directory of the Bash tool of Claude Code, which stayed `TMPDIR=/tmp/claude-501` and `TMPPREFIX=/tmp/claude-501/zsh` with the three set to other directories in two runs of the probe, so that root, `/tmp/claude-<uid>` (`/private/tmp/claude-<uid>` on macOS), is shared by every Claude Code session of the user: it holds a directory per project, named after the working directory with every `/` made `-`, and a directory per session below it, and the runs of the probe left theirs there, so a later run could list what an earlier one wrote. After every run that wrote an init event, whatever its outcome, the task removes that run's own session directory, found as `<root>/*/<session_id>` with the `session_id` of its init event, the uid being that of the task; an id that is not made of letters, digits and `-` removes nothing and stops the task, and a link is not followed. Nothing else in the root is removed, since it holds the sessions of the user's other work, and files that a sandboxed command leaves in the root itself are neither removed nor hidden, because other sessions share the root and the task cannot tell whose they are. What the variables do move is the temporary directory and the sockets of Claude Code itself (`CLAUDE_CODE_TMPDIR` gave `<dir>/claude-501` and `<dir>/cc-socks`) and the compile cache of its node process (`TMPDIR`), so a run is given a directory of its own for both, made in `gsttt-agents-tmp` under the temporary directory of the system, writable by the sandbox, swept with the checkout and removed when the run ends, whether it answered, failed or was stopped; the root is emptied when the task starts, and the names are short because the path of a socket is limited to 104 bytes.
- The init event of a run lists its tools, its MCP servers with their status, its plugins, its skills, its commands and its agents. The task compares all of them with the setup: a tool or a server that is not the setup's, a server that is not connected, a plugin that Claude Code does not ship and the setup was not given, which is compared by its name and by its source (`gsttt@inline` for a plugin given with `--plugin-dir`, so a plugin called `gsttt` that comes from a marketplace is a leak), any skill, command or agent of a plugin but the gsttt plugin's in the `gsttt` setup, and any skill, command or agent that the configuration of the user holds is a leak, and the task stops at the first, naming the setup and what was loaded. The init event is not the first line of a stream, since the hooks of a plugin write events before it, so the stream is read until it is found. The check runs as soon as the event is written, in every run, and ends the process there. The event is written after the first request of the run is sent, so a run the check stops has already spent that request; a check that costs nothing before the first run does not exist, because `claude` writes its init event only when it starts a run. A told run is held to the init event of its setup like an installed one, since the sentence it is given adds no tool. A tool is the setup's by the rule that counts its own calls in the table (`Setup::adds`, below). Every ending is held to the event: a process that exited, was stopped at the limit or was ended after its result without having written one is an error naming the transcript, the time the run took and the tail of its standard error, and never a timeout, since a run that wrote no init event loaded nothing that was checked, so its timeout says nothing about its setup.
- The answer, the tokens and the cost come from the stream: the final message, `modelUsage` summed over the models, `total_cost_usd`, `num_turns`. A run that ended without a result, because it was stopped, keeps the tokens of the messages it streamed, each message counted once at the largest it reached. The duration is the task's own clock, from the start of the process to its result event or, for a run without a result, to its exit or to the limit, so a run stopped at the limit has one too. The transcripts go to `bench/results/agents/`, one `<question>-<setup>-<arm>-<repeat>.jsonl` for each run; the directory is ignored: they hold the paths of the machine.
- Every setup but `plain` is asked in two arms, because a model that has a tool installed may never reach for it. `installed` is the setup as it is. `told` is the same command line with `--append-system-prompt` and one sentence: "The tools whose names start with `{prefix}` answer questions about the code of this repository: load them with ToolSearch, and use them before you search or read files yourself." The prefix is the one the names of the tools of the setup start with: `LSP`, `mcp__codebase-memory-mcp__` and `mcp__plugin_gsttt_gsttt__`, so the sentences of two setups differ in nothing else. `plain` adds no tools and has no told arm; asking for one is an error. A question is asked in seven runs per repeat, in the order `plain`, `lsp`, `lsp` told, `cbm`, `cbm` told, `gsttt`, `gsttt` told, so that a slow hour of the API falls on every arm alike.
- Each run records the tools it called, how many times each, by the name the stream gives it (`Read`, `LSP`, `ToolSearch`, `mcp__plugin_gsttt_gsttt__impact`). Every `tool_use` block of an `assistant` event counts once, by its `id`, since a message comes again in the events that grow it and carries its blocks with it. The count is kept for every outcome, a run without a result included, as the tokens of its messages are. It tells whether a setup's tools were used at all, and whether the sentence of the told arm changed that. The failures of those calls are counted beside them (`toolErrors`, right after `toolCalls`): a `tool_result` block of a `user` event with `is_error` true counts once, by the `tool_use_id` of its call, under the name of the `tool_use` block with that id, since the event that carries it comes again as a message does, and a failure whose call the stream never showed has no name and is not counted. It is kept for every outcome as the calls are. It is a count and no stop: the task ends neither the run nor itself on a failed call, and the table has no column for it.
- A run ends in one of four ways that are recorded: `answered`, `no-answer` (a final message without a block marked `files`), `turn-limit` (`error_max_turns`) and `timeout`. The three that are not an answer score zero. A run that ends in an error of another kind, such as the API failing or `claude` dying, is a fault of the harness or of the account and not a result of its setup, so the task stops naming the transcript and does not record it.
- One loop waits for every process the task starts, `claude` and the test command of the questions about tests: it starts the process in a process group of its own, looks at it every 50 ms and ends the group at the limit. The group is not enough, because the Bash tool of Claude Code starts every command in a session of its own (measured: `kill -s KILL -- -<pgid of claude>` left the shell and its children alive, parented to pid 1), so after the group the loop kills every process whose working directory is the checkout or below it, found with `lsof -a -d cwd -Fpn` on macOS and `/proc/<pid>/cwd` on Linux, never the task itself or one of its parents, and never a process that already stood in those directories when the process of the run was started. Those are listed before the start and spared, since a shell of the user that looks at the checkout is none of the task's parents and nothing tells it from what a run started; a spared process that ends during the run and whose number a process of the run takes is left alive, which is the safe way to be wrong. A sweep by a marker in the environment was tried and finds nothing, since `ps eww` shows an empty environment for the shells and for `perl`. The group and the sweep end the process after a normal exit too, because a job in the background outlives its parent. A job is refused before its process is started, and before any process is listed, when one of its directories is not absolute or not strictly below a directory the task made itself (the roots of the checkouts of the draw and of the runs and the root of the temporary directories of the runs), compared in the canonical form the working directories are read in, so that a wrong directory costs no run; an empty path, `/` or the home directory would otherwise end every process of the user, and the root of a purpose would end those of the other task that shares it. The limit of the sweep is that it looks at working directories: a process that leaves the group and the session and also moves out of the checkout and out of the temporary directory of the run (`cd / && setsid nohup server &`, or a daemon that calls `chdir("/")`) outlives the run, and the environment cannot mark it, as the marker above shows. The benchmarks do not ask for such a process, and none is looked for.
- The result event ends a run. `claude -p` writes it and then stays alive for as long as a task the model left in the background runs (measured: the result at 8.5 s, the exit at the 40 s limit of the probe, so the run was recorded as a timeout although its answer was written). Once the stream holds a result event the process has five seconds to exit and is ended after that, the run is recorded from its result, and its duration ends at the result event, so the wait is no part of it. The limit applies to a run that has written no result. A stream holds one result event: a second is an error that stops the task, naming the run and its transcript, and records nothing for the run, since keeping the later would choose between two answers of one run without saying so.
- Ctrl-C, SIGTERM and SIGHUP are caught while the runs go on: `signal-hook` sets a flag, since `rustix` has no safe way to install a handler and the workspace forbids `unsafe`. The process of a run is in a group of its own, so the signal reaches the task alone and would leave `claude` running; that holds for the hangup of a closed terminal or a dropped ssh connection too, since the group of `claude` is not the foreground group of the terminal and is no job of the shell, so it gets no hangup of its own. The loop looks at the flag at every poll, ends the group and sweeps as at the limit, the run puts the checkout back through its guard, and the task stops with an error that names the signal and records nothing for that run. The handlers are installed when the first run, or the first baseline run of the questions task, starts, so that a signal during the clone and the install still ends the task at once; one that comes between two runs is seen by the next wait, which fails before it starts anything. A second signal does not wait for any of that. The handlers are installed once, whichever run asks first, and for each signal a conditional default handler is registered before the flag, since `signal-hook` runs the handlers of a signal in the order they were registered: the first signal finds the flag clear and sets it, and the second finds it set and takes the default action of the signal, so a run that does not end, or a sweep that waits, cannot hold the task past the second Ctrl-C. A second signal during the sweep, which lists the processes with `ps` and `lsof` and takes a second or more on macOS, ends the task in the middle of it: the group is ended by then, and the commands that left it may stay alive.
- A run is taken for one that hit the usage limit when its final result is an error, or its first message, starts with one of the sentences Claude Code words for the limits of an account (`You've hit your`, `You've reached your`, `You're out of usage credits`, and nine more), or when a `rate_limit_event` says `rejected`. The sentences are read from the Claude Code binary and not seen in a run, since a limit cannot be asked for. The task stops, keeps the runs before that run, and does not record it.
- A checkout is prepared once. The record of the preparation, `.git/gsttt-agents-prepared`, holds the install and build commands it was made with, so another pin prepares again, and a checkout whose `node_modules` is gone is prepared again too, since a run may delete it and the record says nothing of what became of the install after it. What a run that was killed left among the tracked files and the untracked ones is undone first (`git checkout` and `git clean -d`, which leave the ignored install alone).
- The checkout is compared before and after every run and put back whatever became of the run. HEAD is read first, the commit and, when it is not detached, the branch; a run that moved either is marked, and HEAD is put back in the form it had (a branch is reset to its commit, also when the run left or deleted it). Tracked files are reset to HEAD. The untracked and the ignored files are listed one by one with `git ls-files` and not with `git status --porcelain --ignored`, which shows a directory that holds nothing but new or ignored files as one entry and lists its files one by one once a file of another kind comes into it, so a file that was there before the run could be taken for one the run added. The files the run added, ignored ones included, are removed, and so are the directories left empty without them; a directory with anything else in it stays. `git clean` is not run over the tree, since it would take the install and the indexes with it. If the checkout is still not as the preparation left it, as when a run deleted a file that was there before, the task stops naming the checkout. Only the names are compared: what a run changes inside a file that is untracked or ignored, such as one in `node_modules`, is not seen, and a directory that was empty before the run is invisible to git and goes with the files the run put in it.
- The two indexes the runs read are kept aside, because a run of their setup can change them and every run after it would read what it left: the index of gsttt in `.git/gsttt` of each checkout, copied once `gsttt index` has made it, and the cache of codebase-memory-mcp (`CBM_CACHE_DIR`, one directory for the indexes of every checkout), copied once every checkout is indexed. The copies are in `indexes` of the directory of the files of the setups, which no run may read. After a run of the `gsttt` setup the index of its checkout is compared with its copy, file by file and byte by byte, and after a run of the `cbm` setup the cache is; the `plain` and `lsp` runs are given neither index and are not checked against one. A run that changed an index is marked, and the index is put back as the copy is. What the tools write on their own was measured on the unchanged checkout of vite. gsttt writes nothing: after `gsttt index` and a copy, `gsttt hook session-start`, `gsttt impact packages/vite/src/node/index.ts` twice (once with `--no-refresh`) and a second `gsttt index` left `diff -r` of the copy and of `.git/gsttt` empty and `snapshot.gsttt` the same in bytes and in modification time, so any difference of `.git/gsttt` counts as a change. codebase-memory-mcp writes `activity.db`, `activity.db-shm`, `activity.db-wal` and `logs/`: `codebase-memory-mcp cli list_projects` alone created the `-shm` and `-wal` files and changed `logs/cbm-daemon.log`, and a server session that answered `search_graph` and `get_architecture` also changed `activity.db`, while `_config.db`, the database of the project and its log stayed the same byte for byte. Those four names at the top of the cache are neither compared nor put back, and the rest of the cache is. Not measured: what the server writes when it indexes a project again by itself during a run, which would count as a change if it did not stay in those four names. The daemon of codebase-memory-mcp keeps the index open and survives its session (`daemon stop` retires it, and ends with 0 when none runs: measured with 0.12.1 and a home and a cache of fresh directories), so it is stopped before its cache is thrown away, at the start of the task, and before the cache is put back, after each run of the `cbm` setup. The stop runs in the environment the tool runs with, the `HOME` and the `CBM_CACHE_DIR` of the pinned layout, which is also where the daemon is found; a stop that fails stops the task, since the cache would otherwise change under a live daemon. A copy that is missing for the `gsttt` or the `cbm` setup is an error that names the repository and the setup, because nothing would be compared or put back and nothing would say so; only `plain` and `lsp` have no copy. The restore is not atomic: it removes what the index holds and then copies the kept copy in, so a task that is killed between the two leaves half an index. The next task start heals it, because every start throws the cache of codebase-memory-mcp away, indexes both again and keeps new copies.

## Results

- `bench/results/agents.json` is rewritten after every run, so a stopped task loses at most the run it was in, and a started-over task goes on where it stopped. It records the model id and the Claude Code version the init event of the first run names, not the alias, and refuses to add to results of another model, another Claude Code version, another questions file or other versions of the tools, so one table never mixes them. The tools are the versions of the programs, and the SHA-256 of the copy of the binary under test, `gsttt-sha256`, since two builds of one version print the same `--version`: results with another sum are refused as results with another version are. A run whose init event names another model is ended as soon as that event is written, so the refusal adds no run to the results, though the run has spent its first request. A run is added to the results and reported as done only once the file with the run in it is written; when the write fails, the run is taken out of the results again and the task stops with the error, so no run is reported that the file does not hold.
- Each run records the arm it was asked in, the kind of its question, so that the table needs no other file, and whether it changed the checkout: its files, its HEAD or an index.
- Tokens are the four counts as reported added together, cache reads included, because they are what the context of a run costs; the table shows the cost beside them.
- The table has a row per setup and arm that has runs, labelled `gsttt` and `gsttt, told`, in the order the runs go. Beside the means it has three columns of counts of behaviour: `own tool calls`, the mean per run of the calls of the tools the setup adds, which one rule decides in the table and in the init check alike (`Setup::adds`): `LSP` by its whole name for `lsp`, a name that starts with the prefix of its MCP server for `cbm` and `gsttt`, which ends in `__`, so that neither `LSPx` nor a tool of a server whose name begins like theirs is a call of theirs, and nothing for `plain`; `runs that called them`, how many runs made at least one such call; and `changed the checkout`, how many runs changed it. `plain` has no tools of its own, so it shows a dash in the first two. The cost keeps its rule: the mean over the runs that report one.
- The progress of the task goes to standard error, a line for each run that names its question, setup, arm and repeat, and the table of the results to standard output when the task ends.

## Rejected

- Questions written by hand: their answers would be what the writer believed, and a writer who knows gsttt would ask what gsttt answers well.
- Answers from gsttt, codebase-memory-mcp or a grep: each would score its own tool as perfect.
- Runs in parallel: they would compete for the machine and for the rate limit of the account, which shows up as time and as errors that belong to no setup.
