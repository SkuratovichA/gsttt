# Design

## Context

`cargo xtask bench` (`xtask/src/bench.rs`) measures how fast tools build an import graph. It pins public repositories in `bench/bench.toml`, clones them at a commit (`bench/setup.rs`), installs the Node tools with pnpm into `bench/tools/node`, unpacks codebase-memory-mcp into `bench/tools/cbm`, describes the machine (`bench/machine.rs`) and writes a results file through a temporary file that refuses local paths (`bench/results.rs`). The agent benchmark reuses all of it and adds what speed does not need: questions with answers that no tool under test computed, Claude Code runs that see only the tools of their setup, and scores.

## The questions

- Two kinds, both about one exported function: `users`, the other files that refer to it, which an agent needs before it renames or changes a signature; and `tests`, the test files that break when it breaks, which an agent needs to know what to run.
- The answers come from tools that are not under test. `users` uses the TypeScript language service (`findReferences`) of the pinned TypeScript, run by a Node script in `bench/agents/`. `tests` makes the function throw and runs the repository's own tests with the Vitest JSON reporter. Static reachability says which tests could be affected; a failing test is the ground truth that one is. A report that is not Vitest's JSON stops the draw, and so does a run without a throw that reports no test file: neither is a run without failures.
- A test file is in the answer when it fails in both runs with the throw and passes in both runs without it, so a flaky file is in no answer. A file that passes in both runs without the throw and fails in only one of the two runs with it is out of the answer and kept with the question, because the throw or the run may have broken it, and so are the files that fail without the throw: both are scored as neither right nor wrong, since no agent can know them.
- Only TypeScript repositories get questions, because the language server is TypeScript's. Each repository names a scope: `packages/vite` for vite, whose other packages import vite by its package name through `dist`, which the language service cannot follow in a checkout that is not built; the whole checkout for excalidraw, whose tsconfig maps its packages to their sources. Vitest does not start in vite until `packages/vite/dist` exists, because its config imports vite through `dist`, so vite also pins a `build` command that runs once after the install in the checkout of the draw. The runs are made in a checkout of their own, cloned again at the same commit, installed and never built: an agent asked for the users of a function would otherwise find build output beside the sources, and two of the tools under test would index it. Only vite gets questions of the kind `tests`: excalidraw installs with yarn, and its lockfile is the only thing that pins what its tests run against.
- The candidates of a kind are the exported functions of the scope, with `export function` and `export const name = (…) =>` or `= function`, declared in a file that is not a test and not a declaration file; `tests` also needs a block body and a function that is not a generator, since calling a generator runs none of its body (an async function stays, because a throw in its body is a rejected promise). The Node script lists them with their referring files and the offset of their body once, and the draw in Rust takes them in the order of the SHA-256 of `seed`, repository, file and name until enough of them qualify. The script refuses to answer when a relative import or a path of the tsconfig inside the scope does not resolve, since a language service that misses a file gives answers that miss its references.
- A question holds its prompt, so the file shows exactly what the agent was asked. The prompt says what counts (by name: imports, named re-exports, uses; or the unit tests run by the pinned command, when the function fails every time it is called, by throwing an error or, if it is async, by returning a promise that rejects with one), forbids changing files and running the tests, and asks for the last block marked `files`.

## The runs

- Every run is `claude -p` with the pinned model, `--output-format stream-json --verbose`, `--no-session-persistence`, `--permission-mode bypassPermissions`, `--setting-sources project`, `--tools` of its setup, `--max-turns` with the pinned limit, and the prompt on standard input, in the checkout of the runs. `claude --help` of 2.1.312 does not list `--max-turns`, but a run honours it and ends with the result `error_max_turns`.
- The environment of a run is built, not inherited: it holds the variables a program needs to find its home, its login and the network (`HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `LANG`, `LC_ALL`, `TERM`, `CLAUDE_CONFIG_DIR`, the proxy variables, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `NODE_EXTRA_CA_CERTS`), the PATH below, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` and `ENABLE_CLAUDEAI_MCP_SERVERS=false`. Nothing of the session the task runs inside reaches a run, so a run started from inside Claude Code is not taken for a nested one and no `CLAUDE_CODE_*` or `ANTHROPIC_*` variable changes what it loads.
- `plain`, `lsp` and `cbm` pass `--strict-mcp-config` with a config of their own (empty, empty and codebase-memory-mcp). `gsttt` passes `--plugin-dir` with this repository's `plugin/` and no strict config, because a strict config also drops the servers of plugins. `lsp` passes `--plugin-dir` with a plugin the task writes, whose manifest has only `lspServers`, running the pinned typescript-language-server with the pinned TypeScript.
- The PATH is built from the directories of the programs a run needs, never from the PATH of the machine, because `~/.local/bin` holds both `claude` and an installed gsttt: the directory of `node`, which the language server is a script of, and the four system directories. The binary under test is an argument of the task, `--gsttt <binary>`, which `run` requires. It is copied alone into a directory beside the checkouts of the runs, that directory is prepended to the PATH of the `gsttt` setup and of no other, the same copy builds the gsttt index of the checkouts, and its `--version` is recorded among the versions of the tools. A directory of the PATH of another setup that holds a program called `gsttt` stops the task before the first run. The Bash tool of a run builds its shell from a snapshot of `~/.zshrc`, which carries the zsh functions and aliases of the user into every setup alike (232 functions on the machine of the probe, none named after a program of a setup), and whose last line exports the PATH of the `claude` process again: the PATH of the Bash of a run was measured equal to the one the task builds, byte for byte, in all four setups.
- The checkout of the runs lives under the temporary directory of the system: under `~/git` or this repository a CLAUDE.md of a parent directory would reach every run. The task checks the parents for a CLAUDE.md before it prepares anything.
- The isolation was measured, not assumed. The probe asked whether the context of the run held the phrase `No sound, ever`, which only the global CLAUDE.md of the machine holds. With the flags above and the environment of a run it answered "No. The phrase `No sound, ever` doesn't appear anywhere in my context." The same command without `--setting-sources project`, without the strict config and with the environment of the session answered "Yes. The line is in the global rules from `~/.claude/CLAUDE.md`: - **No sound, ever.** Never run `say`, `afplay` …", and its init event listed the MCP servers, the plugins and the skills of the machine.
- The init event of a run lists its tools, its MCP servers with their status, its plugins, its skills, its commands and its agents. The task compares all of them with the setup: a tool or a server that is not the setup's, a server that is not connected, a plugin that Claude Code does not ship and the setup was not given, any skill, command or agent of a plugin but the gsttt plugin's in the `gsttt` setup, and any skill, command or agent that the configuration of the user holds is a leak, and the task stops at the first, naming the setup and what was loaded. The init event is not the first line of a stream, since the hooks of a plugin write events before it, so the stream is read until it is found. The check runs as soon as the event is written, in every run, and ends the process before the model is asked; a check that costs nothing before the first run does not exist, because `claude` writes its init event only when it starts a run.
- The answer, the tokens and the cost come from the stream: the final message, `modelUsage` summed over the models, `total_cost_usd`, `num_turns`. A run that ended without a result, because it was stopped, keeps the tokens of the messages it streamed, each message counted once at the largest it reached. The duration is the task's own clock, from the start of the process to its result event or, for a run without a result, to its exit or to the limit, so a run stopped at the limit has one too. The transcripts go to `bench/results/agents/`, which is ignored: they hold the paths of the machine.
- A run ends in one of four ways that are recorded: `answered`, `no-answer` (a final message without a block marked `files`), `turn-limit` (`error_max_turns`) and `timeout`. The three that are not an answer score zero. A run that ends in an error of another kind, such as the API failing or `claude` dying, is a fault of the harness or of the account and not a result of its setup, so the task stops naming the transcript and does not record it.
- One loop waits for every process the task starts, `claude` and the test command of the questions about tests: it starts the process in a process group of its own, looks at it every 50 ms and ends the group at the limit. The group is not enough, because the Bash tool of Claude Code starts every command in a session of its own (measured: `kill -s KILL -- -<pgid of claude>` left the shell and its children alive, parented to pid 1), so after the group the loop kills every process whose working directory is the checkout or below it, found with `lsof -a -d cwd -Fpn` on macOS and `/proc/<pid>/cwd` on Linux, never the task itself or one of its parents. A sweep by a marker in the environment was tried and finds nothing, since `ps eww` shows an empty environment for the shells and for `perl`. The group and the sweep end the process after a normal exit too, because a job in the background outlives its parent.
- The result event ends a run. `claude -p` writes it and then stays alive for as long as a task the model left in the background runs (measured: the result at 8.5 s, the exit at the 40 s limit of the probe, so the run was recorded as a timeout although its answer was written). Once the stream holds a result event the process has five seconds to exit and is ended after that, the run is recorded from its result, and its duration ends at the result event, so the wait is no part of it. The limit applies to a run that has written no result.
- Ctrl-C and SIGTERM are caught while the runs go on: `signal-hook` sets a flag, since `rustix` has no safe way to install a handler and the workspace forbids `unsafe`. The process of a run is in a group of its own, so the signal reaches the task alone and would leave `claude` running. The loop looks at the flag at every poll, ends the group and sweeps as at the limit, the run puts the checkout back through its guard, and the task stops with an error that names the signal and records nothing for that run. The handlers are installed when the first run, or the first baseline run of the questions task, starts, so that a signal during the clone and the install still ends the task at once; one that comes between two runs is seen by the next wait, which fails before it starts anything.
- A run is taken for one that hit the usage limit when its final result is an error, or its first message, starts with one of the sentences Claude Code words for the limits of an account (`You've hit your`, `You've reached your`, `You're out of usage credits`, and nine more), or when a `rate_limit_event` says `rejected`. The sentences are read from the Claude Code binary and not seen in a run, since a limit cannot be asked for. The task stops, keeps the runs before that run, and does not record it.
- The checkout is compared before and after every run by `git status --porcelain --ignored`. A run that changed it is marked, tracked files are reset to the commit, and files it added are removed, ignored ones included, so that the next run starts from what the indexes were made of.

## Results

- `bench/results/agents.json` is rewritten after every run, so a stopped task loses at most the run it was in, and a started-over task goes on where it stopped. It records the model id and the Claude Code version the init event of the first run names, not the alias, and refuses to add to results of another model, another Claude Code version, another questions file or other versions of the tools, so one table never mixes them. A run whose init event names another model is ended at that event, before the model is asked, so refusing the results runs nothing.
- Each run records the kind of its question, so that the table needs no other file, and whether it changed the checkout.
- Tokens are the four counts as reported added together, cache reads included, because they are what the context of a run costs; the table shows the cost beside them.
- The progress of the task goes to standard error, and the table of the results to standard output when the task ends.

## Rejected

- Questions written by hand: their answers would be what the writer believed, and a writer who knows gsttt would ask what gsttt answers well.
- Answers from gsttt, codebase-memory-mcp or a grep: each would score its own tool as perfect.
- Runs in parallel: they would compete for the machine and for the rate limit of the account, which shows up as time and as errors that belong to no setup.
